\begin{abstract}
\noindent\textbf{Summary:}
FastaGuard is a streaming, explainable FASTA preflight QC tool that validates assembly
FASTA files, detects structural and composition red flags, and emits a versioned
multi-format report with an explicit pipeline gate before expensive downstream
analysis such as QUAST,
BUSCO, BlobToolKit, CheckM, annotation, or official repository validation.

\noindent\textbf{Availability and Implementation:}
Source code and documentation are freely available under the MIT license at
\url{https://github.com/ehsanestaji/FastaGuard}
(release tag \texttt{v1.0.0}:
\url{https://github.com/ehsanestaji/FastaGuard/releases/tag/v1.0.0};
archived at \href{https://doi.org/10.5281/zenodo.23622311}{doi:10.5281/zenodo.23622311}).
Install via Bioconda
(\texttt{mamba install -c conda-forge -c bioconda fastaguard=1.0.0}),
BioContainers, or GitHub release binaries.
Implemented in Rust; supported on Linux and macOS, including Bioconda builds for
\texttt{linux-64}, \texttt{linux-aarch64}, \texttt{osx-64}, and \texttt{osx-arm64}.

\section{Introduction}
Genome assemblies and reference FASTA files are foundational inputs for
bioinformatics pipelines, yet FASTA-level checks are usually assembled from
separate utilities.
Teams commonly combine ad hoc scripts, general sequence utilities such as
SeqKit~\citep{shen2016seqkit,shen2024seqkit2}, assembly evaluators such as
QUAST~\citep{gurevich2013quast}, biological completeness tools such as
BUSCO~\citep{simao2015busco}, genome-quality estimation with
CheckM~\citep{parks2015checkm}, contamination-oriented exploration with
BlobToolKit~\citep{challis2020blobtoolkit}, and late-stage report aggregation with
MultiQC~\citep{ewels2016multiqc}.
Raw-read QC tools remain essential before assembly, but they do not answer
whether a finished assembly FASTA is structurally sound for the next stage.
Each of the tools above is valuable for its intended question; none is designed
as a first-step gate for a narrower but frequent need:
whether a FASTA file is structurally valid, alphabet-sane, interpretable, and
safe to pass into expensive downstream steps.

The cost of skipping that earlier layer is practical.
Malformed headers, empty records, duplicate identifiers, invalid IUPAC
characters, extreme ambiguity, and high-N scaffolds may be caught only when a
downstream tool reaches the offending record, or be silently normalised along
the way; we did not quantify the resulting delay.
Pipeline authors then reimplement the same checks, with incompatible report
shapes and unclear stop/go semantics for workflow engines such as
Nextflow~\citep{ditommaso2017nextflow} and Snakemake~\citep{molder2021snakemake}.
Dedicated validators exist: py\_fasta\_validator~\citep{edwards2023pyfastavalidator}
and fa-lint~\citep{falint} check headers, alphabet, and identifier uniqueness
but, to our knowledge, provide no structured per-finding report, and AssemblyQC
embeds such input checks inside a single pipeline~\citep{rashid2024assemblyqc}.
Statistics toolkits such as SeqKit, SeqFu~\citep{telatin2021seqfu}, and
gfastats~\citep{formenti2022gfastats} mainly summarise sequences and define no
gate semantics.
To our knowledge, none combines severity-graded findings, an explicit
blocking-versus-advisory gate, and a schema-versioned machine-readable report
(JSON, TSV, MultiQC) that workflow engines can branch on.

FastaGuard addresses that gap as a dedicated \emph{preflight} layer
(Fig.~\ref{fig:overview}).
It is intentionally not a competitor to interpretive assembly QC:
it does not claim biological completeness, contamination taxonomy, or repository
acceptance, and it does not replace official NCBI, ENA, or DDBJ validators.
Instead it answers whether the FASTA itself is ready for those tools, and it
returns a versioned PASS/WARN/FAIL contract, with verdicts, gates, and findings
that are deterministic for a given input and options, that humans and
Nextflow, Snakemake, or nf-core~\citep{ewels2020nfcore} workflows can consume
without scraping logs or HTML.
The design is therefore a contract as much as a report:
field names, documented finding identifiers, provenance checksums, and gate
continuation booleans are intended to remain stable within a schema major
version.

\section{Implementation}
FastaGuard is a streaming-first command-line tool implemented in Rust and
distributed as a single binary.
The primary assembly workflow is:

\begin{verbatim}
fastaguard sample.fa --profile assembly --gate pipeline \
  --outdir reports --prefix sample-01
\end{verbatim}

\noindent
which writes a four-report bundle
(\texttt{.html}, \texttt{.json}, \texttt{.tsv}, and MultiQC-compatible
\texttt{\_mqc.json}) under a chosen prefix.
Verdicts, gates, and findings are deterministic for a given input and options;
provenance timestamps and durations vary between runs.
JSON is the source of truth for machine routing.
A committed JSON Schema and finding catalog document field names, finding
identifiers, severity semantics, and suggested actions
(\texttt{fastaguard --schema}, \texttt{--finding-catalog},
\texttt{--explain-finding}).

\paragraph{Validity and composition checks.}
Under the assembly profile, FastaGuard reports structural failures (malformed
headers, empty records, sequence before the first header, empty input),
duplicate identifiers and duplicate sequences, invalid nucleotide/IUPAC
symbols, core length statistics including N50/N90 and L50/L90, and composition
signals (GC/AT/N and ambiguity rates, gap runs, tiny-contig advisories, and
composition or length outlier hints).
Findings are explainable: each carries an identifier, evidence bounds, and
routing language that distinguishes blockers from advisories.

\paragraph{Pipeline gates and process exit contract.}
Optional gates make stop/go policy explicit.
The recommended workflow preset \texttt{--gate pipeline} marks duplicate identifiers
(full-header or first-token), invalid characters, invalid FASTA structure, and
high-N content as blocking by default, while GC and length outliers remain advisory routing signals unless
elevated with \texttt{--fail-on}.
JSON exposes \texttt{gate.status}, \texttt{gate.blocking\_findings},
\texttt{gate.advisory\_findings}, \texttt{gate.can\_continue}, and
\texttt{provenance.input\_sha256}.
From v0.6 onward, process exit codes separate execution from QC status:
exit~0 means report generation completed for PASS, WARN, and FAIL results;
exit~2 covers argument errors; exit~3 covers configuration, I/O, or runtime
failures.
Workflows should therefore branch on \texttt{gate.can\_continue} (or related
gate fields), not on process status alone.
\texttt{machine\_summary.safe\_for\_downstream} is intentionally stricter (true
only for overall PASS) and is not a synonym for gate continuation.

\paragraph{Submission-readiness, compare mode, and reference checks.}
\texttt{--gate submission} with \texttt{--submission-target generic|ncbi}
performs FASTA-level submission preflight before official validators.
For NCBI genome targeting, FastaGuard applies a documented, deliberately
conservative \texttt{ncbi\_genome} policy snapshot (first-token SeqID syntax and
length limits, minimum record length, terminal Ns) based on NCBI submission and
FASTA guidance~\citep{ncbi_genome_submit,ncbi_fasta_format}; in a local
differential check it was stricter than table2asn~\citep{ncbi_table2asn} on several boundary cases
(for example, a 199-bp record or a 50-character SeqID), and it does not replace
NCBI FCS~\citep{astashyn2024fcsgx}, annotation validation, or repository
acceptance decisions.
\texttt{fastaguard compare} triages many FASTA files into cohort HTML/JSON/TSV
outputs for starter cohort routing before interpretive QC.
A separate \texttt{reference} mode checks whether explicitly supplied companion
declarations (FASTA index, sequence dictionary, alignment/variant headers,
GFF3 sequence declarations) agree with a canonical FASTA under
\texttt{strict}, \texttt{coordinate}, or \texttt{advisory} policies.

\paragraph{Readiness categories.}
Beyond a single verdict, reports expose readiness facets spanning file,
structure, alphabet, index, assembly, submission, and machine concerns.
That decomposition helps operators see \emph{why} a file is not yet ready
(for example, identifier hazards versus composition advisories) without reading
an unstructured log.
HTML reports remain human-oriented, while JSON/TSV remain stable for engines
and for MultiQC custom content.

\paragraph{Packaging and workflow adoption.}
FastaGuard is published on Bioconda~\citep{gruning2018bioconda} and
BioContainers~\citep{daveigaleprevost2017biocontainers}, ships GitHub release
binaries for x86\_64 Linux and for Intel and Apple-silicon macOS (Linux aarch64
is available through Bioconda), and has merged nf-core and Snakemake wrapper
integrations for assembly preflight.
A typical install path is
\texttt{mamba install -c conda-forge -c bioconda fastaguard=1.0.0}
(matching GitHub release tag \texttt{v1.0.0}), with a pinned BioContainers image
for containerized workflow engines.
These distribution paths are part of the Application Note claim: the tool is
meant to be installed and gated in pipelines with low friction, not only built
from source by specialists; we make no claim about third-party adoption.
The archived release is citable~\citep{fastaguard2026}, and source and
published packages remain openly reachable under the MIT license.

\section{Results}
Committed public-evidence summaries for FastaGuard v0.6.0 illustrate the intended
behaviour on synthetic contract fixtures and two exact NCBI RefSeq
assemblies~\citep{oleary2016refseq} (Table~\ref{tab:evidence}).
Portable JSON and TSV summaries in the repository record input byte sizes,
SHA-256 digests, structural metrics, finding identifiers, and scoped provenance
separately for the observed executable and the verified source tree.
On a recorded macOS arm64 run, a clean \emph{Escherichia coli} K-12
MG1655~\citep{blattner1997ecoli} assembly (\texttt{GCF\_000005845.2}; 4\,641\,652~bp) completed pipeline-gated
preflight in 0.0569~s with PASS and no findings.
A \emph{Neurospora crassa} OR74A~\citep{galagan2003neurospora} assembly (\texttt{GCF\_000182925.2}; 41\,102\,378~bp)
completed in 0.3441~s with WARN for gap-pattern advisories and
\texttt{gate.can\_continue} still true under the pipeline gate, routing to deeper
assembly or composition follow-up rather than hard failure.
An intentionally broken local fixture returned FAIL with blocking findings
(duplicate identifiers, invalid characters, high-N content) while still exiting~0 after
writing a complete FAIL report---matching the v0.6 workflow contract that
separates QC status from process success.
Re-running all five evidence-pack inputs with a build of the v1.0.0 tag reproduced
the same verdicts, gate statuses, blocking findings, lengths, sequence counts,
input SHA-256 digests, and exit status; timings differed between runs and are
indicative only.

These examples are contract demonstrations, not a representative biological
benchmark across taxa or assemblers.
They show that clean references can pass quickly, that advisory gap patterns can
WARN without blocking continuation, and that FASTA-level blockers remain machine
visible in FAIL reports that workflow engines can parse.
Compare mode and submission gates extend the same contract to cohort triage and
FASTA-level submission hazards; reference mode adds companion-declaration
compatibility checks when indexes, dictionaries, or headers must agree with a
canonical FASTA before mapping or annotation workflows proceed.

To place these behaviours against existing tools, we ran
py\_fasta\_validator~0.6, fa-lint~1.2.0, table2asn~1.29.324~\citep{ncbi_table2asn},
SeqKit~2.14.0, and FastaGuard v1.0.0 on 30 small constructed FASTA files
(7 valid, 13 defective, and 10 advisory files that are not scored;
Table~\ref{tab:comparison}), with expectations written down before any tool was
run.
No tool flagged a valid file.
FastaGuard's NCBI gate flagged all 13 defective files and its pipeline gate 11
(blocking 10); fa-lint flagged 9, table2asn 7, and py\_fasta\_validator and SeqKit
5 each.
table2asn returned no validation result on three inputs: an empty file, which it
could not open, and two duplicate-identifier files, on which it did not terminate
within the 30~s limit.
Only FastaGuard's NCBI gate flagged a 50-character SeqID and a SeqID containing
\texttt{@}; table2asn accepted both.
FastaGuard did not flag blank lines inside records or uneven line wrapping, which
fa-lint does.
On the two RefSeq assemblies, no tool flagged \emph{E.\ coli}; in \emph{N.\ crassa},
py\_fasta\_validator, fa-lint, and SeqKit flagged nothing, whereas table2asn
reported error-level internal runs of 100~Ns (\texttt{InternalNsInSeqRaw}), which
FastaGuard reports as non-blocking gap-pattern advisories (WARN).
The corpus was built by the FastaGuard authors, its NCBI-rule rows encode the
policy that FastaGuard's NCBI gate implements, and the tools serve different
purposes, so Table~\ref{tab:comparison} compares capabilities, not accuracy on
real submissions.

A minimal workflow pattern is therefore: run FastaGuard with
\texttt{--gate pipeline} and an output bundle; inspect
\texttt{gate.can\_continue} in JSON (for example with \texttt{jq}); only then
launch QUAST, BUSCO, BlobToolKit, CheckM, annotation, or official validators.
If the gate fails, fix the FASTA-level blockers first.
If the gate continues with WARN advisories, keep the findings as routing hints
for which interpretive tool to prioritize next.
In practice, a PASS or non-blocking WARN means only that the selected FastaGuard
gate policy was satisfied and that the FASTA can be routed to appropriate
downstream tools.
It does not establish assembly correctness, biological completeness,
contamination status, taxonomy, annotation quality, or archive acceptance.
That boundary is deliberate: FastaGuard owns FASTA-level preflight and triage;
interpretive tools own interpretive questions.

\section{Discussion}
FastaGuard's contribution is a pipeline-native FASTA preflight \emph{contract}:
streaming validation, explainable findings, stable schemas, explicit gates, and
packaging paths that workflow authors can adopt without reinventing per-pipeline
scripts.
Relative to SeqKit and SeqFu, FastaGuard trades general sequence manipulation
for an opinionated QC verdict and gate policy; relative to syntax validators
such as py\_fasta\_validator and fa-lint, it adds severity-graded, explainable
findings and a structured report (Table~\ref{tab:comparison}).
Relative to QUAST, BUSCO, BlobToolKit, and CheckM, it runs earlier and answers a
different question: whether the FASTA is safe to spend those tools on.
Relative to MultiQC, it is a producer of aggregatable content rather than an
aggregator.
Positioning the tool as preflight---rather than as a substitute for those
ecosystem components---keeps it complementary to them.

Limitations follow from that scope.
FastaGuard does not discover biological contamination, does not certify archive
acceptance, and does not replace official validators or FCS-style screens.
Public-evidence timings are contextual to one machine and release line; authors
should re-measure on their targets before citing absolute performance.
Finding thresholds are heuristics: we did not measure detection or
false-positive rates on real submissions, and the validator comparison
(Table~\ref{tab:comparison}) uses a small author-constructed corpus.
The behaviour described here corresponds to release v1.0.0; later changes are
recorded in the project changelog.
